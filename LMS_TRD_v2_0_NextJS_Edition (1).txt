1. Executive Summary
This TRD v2.0 replaces TRD v1.0 entirely. The fundamental product scope (PRD v1.0) is unchanged. What changes is the entire infrastructure and technology layer: the Django REST Framework backend is replaced by Next.js Route Handlers, making the system a true full-stack Next.js application. The database ORM is Drizzle (provider-agnostic), and attendance tracking is fully automated through Zoom's event webhook system.
1.1 Core Design Principles
* No vendor lock-in on the database: Drizzle ORM uses a standard PostgreSQL connection string (DATABASE_URL). Switching between Neon, Railway, Supabase, Google CloudSQL, Amazon RDS, or any other PostgreSQL host requires changing exactly one environment variable.
* Free tier first: every service selected has a meaningful free tier sufficient for Phase 1 (â¤200 active users). Paid tiers are documented as scale thresholds, not starting costs.
* Single runtime, single deployment: all server logic â API routes, webhook handlers, middleware, cron endpoints â runs inside Next.js. One Vercel project, one codebase, one CI pipeline.
* Automated attendance via Zoom: no manual check-in required. Zoom's participant_joined / participant_left events drive the attendance ledger in real time.
* Real-time via Firestore: chat and live notifications use Firebase Firestore's native real-time listeners. No self-hosted WebSocket server required â compatible with Vercel's stateless serverless model.
* Scheduled jobs via QStash: Upstash QStash replaces Celery + Redis for all background work (report generation triggers, calendar renewal, session reminders). HTTP-based, works with Vercel serverless.

2.2 Why Drizzle ORM is Selected
2.2.1 Serverless-First Architecture
Prisma ships a 40MB Rust query engine binary. On Vercel's free tier this causes slow cold starts and occasionally fails deployment size checks. Drizzle has no binary engine â it compiles to plain JavaScript and connects directly through the PostgreSQL driver you choose.
2.2.2 True Provider Portability
Drizzle connects through the driver layer, not through a managed service. The same schema and queries work with:
* Neon (free tier, serverless PostgreSQL, built-in connection pooling)
* Railway (free $5/month credit, standard PostgreSQL)
* Supabase PostgreSQL (connect via direct URL, ignore Supabase-specific features)
* Google CloudSQL for PostgreSQL
* Amazon RDS PostgreSQL
* Self-hosted PostgreSQL on any VPS
Switching providers: change DATABASE_URL in Vercel environment variables. No code changes.
2.2.3 Serverless Connection Handling
PostgreSQL has a hard connection limit. Vercel functions spin up fresh instances for every invocation. Drizzle natively supports the @neondatabase/serverless driver (which uses HTTP instead of persistent TCP), and also supports connection pooling URLs from PgBouncer (which all major PostgreSQL hosts expose). This is configured per-environment with a single env var.
2.2.4 SQL Transparency
Drizzle's query syntax is intentionally SQL-like. There is no magic or hidden N+1 query generator. Complex joins, sub-queries, and window functions are all expressible without falling back to raw SQL.
2.3 PostgreSQL Provider Selection
Recommended for Phase 1: Neon free tier. The @neondatabase/serverless driver resolves Vercel's connection exhaustion problem with zero configuration. When you grow beyond the free tier or want to switch, export your data with pg_dump and point DATABASE_URL at any other PostgreSQL host. Drizzle migrations are plain SQL files â they run on any PostgreSQL.

6.3 Webhook Handler â /api/webhooks/zoom
6.3.1 Signature Verification
Every Zoom webhook POST includes an x-zm-request-timestamp header and an x-zm-signature header. Before processing any payload the handler verifies:
* Construct message: v0:{timestamp}:{raw_body_string}
* Compute HMAC-SHA256 of message using ZOOM_WEBHOOK_SECRET
* Compare with x-zm-signature header value (constant-time comparison)
* Reject requests where timestamp is more than 5 minutes old (replay attack protection)
* Respond 200 OK within 3 seconds â Zoom expects immediate acknowledgment. Heavy DB work runs after responding.
6.3.2 User Matching Logic
Zoom sends participant email (if the user is logged into Zoom with a known email) or display name. The matching strategy:
* Primary: match zoom_participant.email to users.email in PostgreSQL
* Fallback: match zoom_participant.display_name to users name (fuzzy, log unmatched for admin review)
* Unmatched participant: logged in zoom_attendance with user_id = null, flagged for admin review
* Meeting host (educator): always identified by zoom_meeting_host_id matched to educator zoom_user_id field
6.3.3 Session Creation with Zoom
When an educator schedules a session in the LMS, the Route Handler automatically creates a Zoom meeting:
* POST to Zoom API: /v2/users/{educator_zoom_user_id}/meetings with topic, start_time, duration
* Store zoom_meeting_id and zoom_meeting_url in sessions table
* The zoom_meeting_url is shown to educator and learner as the session join link
* Educator's Zoom account: connected via OAuth in Educator Settings (Zoom connection tab â new feature in Educator Portal)

7.3 Firestore Security Rules
Firestore Security Rules enforce that users can only read/write their own data. The rules reference Auth.js session user IDs which are also used as Firebase Auth UIDs (via Firebase Admin SDK custom tokens).
* Chat read access: auth.uid in resource.data.member_ids
* Chat write access: auth.uid in resource.data.member_ids (validated against PostgreSQL-assigned course chat members)
* Notification read: auth.uid == userId (document path segment)
* Admin access: custom claim role == 'admin' bypasses member checks for admin oversight
Auth Bridge: When a user logs in via Auth.js, the server calls Firebase Admin SDK to create a custom token for that user's UID (= Auth.js session user ID). The client exchanges this for a Firebase ID token via signInWithCustomToken(). This bridges Auth.js sessions with Firestore Security Rules.

11. File Storage â Cloudflare R2
Cloudflare R2 is S3-compatible with zero egress fees and 10GB free storage. The Next.js Route Handler generates pre-signed PUT URLs; the client uploads directly to R2 â the backend never proxies file bytes.

13.2 AI Report Generation â Timeout Mitigation
AI report generation (30 seconds) may exceed Vercel Hobby's 10-second function timeout. Mitigation strategies:
* Use Vercel Pro ($20/mo) which raises the timeout to 300 seconds â sufficient for Claude streaming.
* Alternative (free): Use QStash to offload the AI call. Admin triggers POST /api/v1/reports/generate â Route Handler publishes a QStash message â QStash delivers to POST /api/cron/run-ai-report â that endpoint calls Claude (no timeout risk as QStash delivery has no timeout). Report saved to DB. Admin polls for completion.
* Recommended: Start with QStash approach (works on free Hobby). Switch to direct streaming on Pro when upgrading.
13.3 Database Connection â Vercel Serverless Constraint
Each Vercel function invocation potentially creates a new PostgreSQL connection. Without a connection pooler, this hits the database connection limit quickly at scale.
* Phase 1 solution: Use Neon's built-in connection pooler (@neondatabase/serverless driver with HTTP transport). Zero connection pool exhaustion.
* Any other provider: use the provider's PgBouncer URL in DATABASE_URL. Drizzle works identically with both direct and pooled URLs.
* Do NOT use the direct database URL in production Vercel deployments â always use the pooled endpoint.
