    PART ONE — ADMIN PORTAL

This section documents every module, workflow, and configuration available to Owner and Admin roles within the LMS administration dashboard.

1. Platform Overview
A full-stack LMS built for tutoring organisations, coaching centres, and ed-tech businesses. Three course formats, three portals:
• Admin Portal — owners and admins manage the entire operation (this document, Part 1).
• Educator Portal — tutors manage schedule, sessions, and learner communication (this document, Part 2).
• Learner / Parent Portal — students and guardians access courses, sessions, and reports (separate PRD).

ⓘ  The testing platform (mock tests, e-books, flashcards) is explicitly out of scope for this document.

4. Calendar (Admin View)
Unified scheduling calendar displaying all sessions across all courses and educators. Distinct from the educator-facing calendar (Part 2, §19).
4.1  View Modes & Navigation
4.2  Session Tile Display
Each session tile shows: scheduled time, learner first name, course short-code, status icon (✓ completed / ✗ cancelled/no-show), and a colour-coded background (each course/educator mapped to a distinct colour).
4.3  Overflow & Density Rules
• Days exceeding visible tile space show an overflow indicator (e.g., "+3 more") — clicking expands the full day list.
• Minimum supported density: 10 sessions per day in month view without visual degradation.
• Sessions booked outside an educator's configured availability (admin override) are visually flagged with a warning indicator.
4.4  Google Calendar Sync
• Sessions created or modified in the LMS reflect in connected educator Google Calendars (2-way).
• Events created or modified in Google Calendar update corresponding session records in the LMS.
• Educator calendar connection status visible in Users → Educators (green filled = connected, grey hollow = not connected).

5. Availability (Admin View)
Allows filtering and reviewing educator availability by subject tag. Educators configure their own detailed availability from the Educator Portal (Part 2, §20).
5.1  Educator Tag Filter
Multi-select tag filter to narrow the availability view to educators with specific subject specialisations. Tags are defined and assigned when adding or editing an educator profile. Categories include:
• Core academic: Maths, Science, Physics, Chemistry, Biology
• Languages: English, French, Telugu (and other languages configured by admin)
• Curriculum-specific: IB, IGCSE, CBSE, ICT
Each tag is colour-coded. Tags are fully configurable by admin.
5.2  Availability Display
• After filtering by tag(s), the view shows free/busy blocks per matching educator per day.
• Admins cross-reference with the Calendar to schedule sessions in available slots.
• Educators with Google Calendar connected show real-time availability automatically.
• Educators without Google Calendar connected rely on manually configured availability profiles (set in Educator Portal).

6. 1-On-1 Personalised Courses
The primary course type. Each course links a single learner to one or more educators. Admin manages the full lifecycle: creation, educator assignment, session scheduling, credit tracking, and public selling page.
6.1  Course List — Columns
6.2  Credits System
• Credits are the billing unit for sessions. One session typically consumes one credit.
• Format: Used/Total (e.g., 3/24 = 3 of 24 purchased credits consumed).
• Fractional credits supported (e.g., 0.5, 1.5) for partial or split-credit sessions.
• Negative balances trigger an admin alert — not silently accepted.
• Credit deduction triggered automatically when session is marked complete by the educator.
• Admins can manually adjust credit totals for a course.

6.5  Course Selling Page Wizard (7 Steps)
Triggered by "+ Add" or by editing a course. "Preview Public Page" button available at any step.

Step 5 — Course Highlights

Step 6 — Reviews
• Select reviews to display on the public course page. Tied to the Rating column in the course list.
Step 7 — Coupons
• Discount codes (percentage or flat-amount). Set validity window and usage limits per coupon.

17. Non-Functional Requirements — Admin Portal
17.1  Performance
• Calendar: 100+ session tiles per month view in under 1 second.
• Global search results: within 300 ms of keystroke.
• Session list pagination (100+ sessions): each page loads in under 500 ms.
• AI report generation: completes within 30 seconds per report.
17.2  Scalability
• Must support 500+ learners, 50+ educators, and 1,000+ courses without architecture changes.
• Calendar must gracefully handle 30+ events per day in month view with overflow indicator.
17.3  Security
• RBAC enforced at API level — not just UI-level hiding.
• Private Notes on learner profiles: admin-only, never surfaced in learner-facing outputs.
• Confidential feedback (educator-about-learner, learner-about-educator): row-level security at data layer — not just UI hiding.
• API keys and webhook secrets encrypted at rest. OAuth tokens auto-refreshed.
• Payment gateway credentials must meet PCI-DSS requirements.
17.4  Usability
• Ctrl+K keyboard shortcut for global search. All modals support keyboard navigation and Escape to close.
• Session status indicators use both colour and icon — not colour alone (accessibility).
17.5  Data Integrity
• Negative credit balances trigger admin alerts — not silently accepted.
• Duplicate learner detection (same email/phone) enforced at "Add Learner".
• Session credit deduction is atomic — no partial deductions on system failure.
• CSV bulk import: validate all rows before committing any; fail-fast with per-row error reporting.

29. Cross-Cutting Rules (Both Portals)
29.1  Read-Only vs. Editable Boundary
• Payouts, session credit totals, and per-course payout rates are Admin-controlled and Educator-read-only everywhere across both portals.
• Educator profile phone and email are read-only (OTP-verified at signup).
29.2  Confidentiality Boundary
• Steps 5–6 of the post-session feedback loop (educator-about-learner, learner-about-educator) are the only strictly one-directional, Admin-only-visible data across both portals.
• All other educator-created content (Timeline posts, Chit Chats, session feedback in §26.1.1, published session reports) is visible to assigned learners by design.
• Admin Private Notes on learner profiles are never visible to the learner or parent.
29.3  Booking-Constraint Enforcement
• Availability (§20) + Preferences (§28.3) together fully define when an educator can be booked.
• Session Conflicts (§22) is the safety net for when something gets booked outside those rules.
• All booking constraints are enforced by the booking engine at API level — not just UI validation.
29.4  Chat Scoping
• Educators can only chat with learners tied to their assigned courses.
• Admins can initiate chats with any educator or learner on the platform.
• All chats are visible to Admins via the "All Chats" view.
